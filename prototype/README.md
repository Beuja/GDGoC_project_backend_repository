## 1. 결론

**프론트는 실제 데이터를 받아도 바로 동작한다. 단, 층 단면도 위치 하나는 프론트 수정이 필요하다.**

| 확인 항목 | 결과 |
|---|---|
| 응답 형식이 프론트 타입(`api.ts`)과 맞는가 | ✅ 응답 12,809개 검사, **불일치 0건** |
| 장소끼리 모두 경로가 나오는가 | ✅ 57곳 × 56 = 3,192쌍 **전부 경로 있음** (기본·편한 길·차도 피하기) |
| 이미지 주소가 프론트에서 열리는가 | ✅ 프론트 `vite.config.ts`가 `/api`, `/static`을 8000번으로 넘겨 줌 |
| 에러 코드 | ✅ `SAME_PLACE`, `PLACE_NOT_FOUND`, `BUILDING_NOT_FOUND`, `VALIDATION_ERROR`, `NO_ROUTE` |
| 경로 선 연결 | ✅ 구간 경계 점 일치, 지도 밖 좌표 없음, 단계의 구간 번호 정상 |
| **층 단면도 위치** | ❌ **프론트 수정 필요** (아래 3-1) |

| 원본 | 가져온 결과 | 비고 |

| `assets/images/` | 지도, 건물, 층 단면도 34장, 건물 사진 | **영문 파일 이름**으로 복사 |

### 변환하면서 보강한 것
- **주석 처리 버그 회피:** 원본의 `//*****` 줄 주석을 블록 주석으로 잘못 읽으면 신공학관 구간이 사라진다. 앞에서부터 차례로 읽는 방식으로 처리했다.
- **화면용 이름:** `법학관_만해관` → `법학관·만해관`, `정보문화관p` → `정보문화관 P` (원본 이름은 `sourceName`에 보관)
- **별칭 예시:** `신공`, `중도`, `학식` 등 (팀이 더 채워야 함)
- **층 단면도 위치 정보(`imageBounds`)** 계산: 원본 앱은 단면도를 건물 이미지 자리에 원래 크기로 겹쳐 그린다.

### 원본 데이터 문제 (경고)
- 중복 간선 2개 (`체육관쪽 입구1 ↔ 체육관쪽 입구`): 처음 것만 사용
- 반대 방향이 없는 간선 6개 (명진관 좌측, 신공 4층 입구 계단, 원흥관 4층 중앙 계단 주변): 현장 확인 필요

### 원본 데이터 보완 (`manual/edge_fixes.json`)
원본은 그대로 두고 변환할 때 보완을 적용한다. 항목마다 이유를 적는다. 백엔드의 `seeds/manual/edge_fixes.json`(백엔드_설계 5.4)과 같은 역할이다.

| 문제 | 증상 | 보완 |
|---|---|---|
| 신공학관 중앙 계단: `신공 4층 계단`이 3층으로 적혀 있고, 계단이 3층→7층으로 바로 이어짐 | 신공학관 4층 → 9층(또는 대운동장)으로 갈 때 **3층으로 내려갔다가** 올라가는 경로가 나옴 | 층을 4로 고치고, 3↔7 연결을 4↔7로 교체 (뒷계단 값 복사). 수정 후 4층→9층 67초, 4층→대운동장 294초 → 285초 |

**현장 확인 필요** (이름의 층과 데이터의 층이 다름. 계단참이나 경사지 입구라 일부러 그렇게 적었을 수도 있음)

| 지점 | 이름 | 데이터 |
|---|---|---|
| 다향관 3층 오른쪽 계단 | 3층 | 2층 |
| 만해관 2층 입구 안 | 2층 | 1층 |
| 사회과학관 3층 쪽문 계단 앞 | 3층 | 2층 |
| 혜화관 3층 계단 | 3층 | 4층 |

## 3. 보강 필요

### 3-1. [프론트, 필수] 층 단면도 위치 ❌
- **문제:** `Map2DViewer.tsx`(254~256행 부근)가 층 단면도를 **지도 전체 크기(0,0 ~ 3000,5333)로 늘려서** 겹친다. 그런데 원본 단면도는 **건물 하나 크기**(예: 신공학관 442×342px)라서, 실제 데이터에서는 단면도가 캠퍼스 전체를 덮는다.
- **제안 (API 필드 추가, 하위 호환):**
  ```ts
  // RouteSegment, BuildingFloorInfo에 추가
  floorImageBounds: { x: number; y: number; width: number; height: number } | null;
  ```
  프론트는 이 값으로 `L.latLngBounds([y, x], [y + height, x + width])`를 만들어 겹치면 된다. 데이터는 이미 계산되어 있다(`data/buildings.json`의 `floors[].imageBounds`).
- 프론트 레포는 직접 고치지 않았다. **프론트 팀원에게 전달할 내용이다.**
- ✅ **복사본(`frontend_test/`)에서 고쳐서 확인함 (2026-11-13).** 검증용 서버는 이미 `floorImageBounds`를 보낸다. 프론트에서 바꿀 곳은 두 군데다.
  1. `src/shared/types/api.ts`: `ImageBounds` 타입 추가, `RouteSegment`와 `BuildingFloorInfo`에 `floorImageBounds?: ImageBounds | null` 추가 (선택 필드라 mock은 그대로 동작)
  2. `src/widgets/map-2d-viewer/Map2DViewer.tsx` 층 단면도 부분: `floorImageBounds`가 있으면 `L.latLngBounds([y, x], [y + height, x + width])`로 겹치고, 없으면 기존처럼 지도 전체에 맞춘다
- ✅ API 명세서 0.4에 반영됨 (2026-11-13).

### 3-2. [데이터] 지름길 데이터가 아직 없음
- 원본에는 지름길 표시가 없어서 지금은 `isShortcut`이 항상 `false`, `savedSeconds`가 항상 `0`이다.
- 프론트의 지름길 강조 스타일은 실제 데이터로는 아직 확인할 수 없다. `shortcuts.json`(백엔드_설계 5.4)을 만들어야 한다.

### 3-3. [데이터] 강의실·도착 힌트 없음
- 목적지는 건물·층 단위까지만 있다. `hint`는 모두 `null`이라 도착 문구가 "도착: 신공학관 4층" 형태로 나온다.

### 3-4. [API 명세] 층 단위 장소의 카테고리
- `신공학관 4층` 같은 층 단위 장소 29곳이 `BUILDING` 카테고리로 나간다(맞는 카테고리가 없음). 지금도 동작하지만, 검색 결과에서 건물과 층을 구분하고 싶으면 `PlaceCategory`에 `FLOOR`를 추가하는 것을 검토한다.

### 3-5. [성능] 지도 이미지 용량
- `campus.png`가 약 5MB다. 모바일에서 느릴 수 있으니 WebP 변환이나 타일 분할을 검토한다.

### 참고: 옵션별 결과
- 차도 피하기(벌점 × 3): 경로 없음 0건, 455쌍은 차도를 아예 피해서 안내
- 계단 피하기: 538쌍(16.9%)은 경로 없음(`NO_ROUTE`). 계단으로만 갈 수 있는 곳이 있어서 정상이다.

## 4. 사용법

Python만 있으면 된다(추가 설치 없음). **backend 레포 폴더에서** 실행한다. 원본 Dubeogi와 frontend 레포가 backend 옆 폴더에 클론되어 있다고 가정한다 (`../Dubeogi`, `../frontend`).

```bash
# 1) 원본 → 데이터 변환 (Dubeogi 폴더 필요)
python -I prototype/convert.py ../Dubeogi prototype/data prototype/static

# 2) 프론트 타입과 대조 → prototype/check_report.md 생성
python -I prototype/check_contract.py ../frontend/src/shared/types/api.ts prototype/data prototype/check_report.md

# 3) 검증용 API 서버 실행 (http://127.0.0.1:8000/api/v1)
python -I prototype/server.py
```

**프론트를 실제 데이터로 띄워 보려면:** 3)의 서버를 켜 두고, 프론트 폴더의 `.env`에 `VITE_USE_MOCK=false`로 두고 `npm run dev`를 실행한다. (프론트 팀원이 자기 PC에서 한다)
