# 백엔드 협업 가이드

GDGoC 팀 1234 백엔드 개발자 2명이 FastAPI 프로젝트를 충돌 없이 함께 진행하기 위한 가이드.
AI 도구용 규칙은 루트의 [`CLAUDE.md`](../CLAUDE.md)에 있다.

---

## 1. 기술 스택

| 분류 | 기술 | 이유 |
|---|---|---|
| 언어 | **Python 3.12** | 안정적이고 라이브러리 호환성이 좋다 |
| 패키지 관리 | **uv** | pip/venv보다 훨씬 빠르고, `uv.lock`으로 두 사람의 패키지 버전을 똑같이 맞춰 준다 |
| 웹 프레임워크 | **FastAPI** + `fastapi[standard]` | 정해진 스택. `/docs`에 Swagger 문서가 자동 생성된다 |
| 검증 / 설정 | **Pydantic v2**, **pydantic-settings** | 요청/응답 검증, `.env` 설정 로딩 |
| DB | **PostgreSQL 16** | 무료 배포처(Supabase, Neon, Render 등)가 많다 |
| ORM | **SQLAlchemy 2.0 (async)** + `asyncpg` | FastAPI에서 가장 많이 쓰는 조합 |
| 마이그레이션 | **Alembic** | DB 스키마 변경 이력을 코드로 관리한다 |
| 인증 | **JWT** (`pyjwt`) + 비밀번호 해시 (`pwdlib[argon2]`) | FastAPI 공식 문서 방식 |
| 테스트 | **pytest**, `pytest-asyncio`, `httpx` | API 테스트 |
| 린트 / 포맷 | **ruff** | 둘의 코드 스타일을 자동으로 맞춰 준다 (충돌 감소에 중요) |
| 커밋 전 검사 | **pre-commit** | 커밋할 때 ruff를 자동 실행한다 |
| 로컬 DB 실행 | **Docker Desktop** + docker compose | 둘이 같은 DB 환경을 쓴다 |
| CI | **GitHub Actions** | PR마다 린트·테스트 자동 실행 |

필요할 때 추가할 것: Redis(캐시·세션), 파일 업로드 시 S3/Cloudinary, 소셜 로그인 시 `authlib`.

## 3. 최초 세팅 (한 사람이 1번만 하고 PR로 올린다)

> 둘이 동시에 세팅하면 바로 충돌이 난다. **한 명이 세팅 PR을 올리고, 다른 한 명은 리뷰한 뒤 pull** 받는다.

```bash
uv init --python 3.12 --no-workspace .
uv add "fastapi[standard]" pydantic-settings "sqlalchemy[asyncio]" asyncpg alembic pyjwt "pwdlib[argon2]"
uv add --dev pytest pytest-asyncio httpx ruff pre-commit
uv run alembic init -t async migrations
```

만들 파일:
- `app/` 폴더 구조 (`CLAUDE.md` 참고), 기존 `main.py`는 `app/main.py`로 옮긴다
- `.env.example` – 필요한 환경변수 목록 (값은 비워 두거나 예시값)
- `docker-compose.yml` – PostgreSQL
- `.pre-commit-config.yaml` – ruff
- `pyproject.toml`에 ruff 설정 (`line-length = 100` 등)
- `.github/workflows/ci.yml` – ruff + pytest

**나머지 한 명은** pull 받은 뒤:
```bash
uv sync
cp .env.example .env          # 값 채우기
docker compose up -d db
uv run alembic upgrade head
uv run pre-commit install
uv run fastapi dev app/main.py
```

## 4. 충돌 안 나게 작업하는 법

### 4-1. 일을 "도메인" 단위로 나눈다

가장 효과가 크다. 같은 파일을 동시에 고치지 않으면 충돌이 거의 나지 않는다.

```
A: domains/user/, domains/auth/
B: domains/post/, domains/comment/
```

- 작업 시작 전에 GitHub Issue를 만들고 담당자를 지정한다.
- 남의 도메인 코드를 고쳐야 하면 먼저 말하고, 상대가 고치게 하거나 작은 PR로 따로 올린다.

### 4-2. 공용 파일은 "먼저 말하고" 고친다

충돌이 자주 나는 파일과 대처법:

| 파일 | 규칙 |
|---|---|
| `app/main.py` | 라우터 등록 한 줄만 추가한다. 다른 수정은 미리 공유한다 |
| `app/core/*`, `app/common/*` | 공용 코드. 수정 전에 공유하고 PR을 작게 만든다 |
| `pyproject.toml`, `uv.lock` | 패키지는 `uv add`로만 추가한다. `uv.lock` 충돌이 나면 직접 고치지 말고 main 버전을 받은 뒤 `uv lock`을 다시 실행한다 |
| `migrations/versions/*` | **가장 위험하다.** 아래 4-3 참고 |
| `.env.example` | 새 환경변수를 추가하면 PR 설명에 적는다 |

### 4-3. Alembic 마이그레이션 규칙

두 사람이 동시에 마이그레이션을 만들면 "head가 2개"가 되어 `upgrade`가 실패한다.

- 마이그레이션을 만들기 직전에 **반드시 main을 pull** 받는다.
- 마이그레이션이 포함된 PR은 빨리 머지한다 (오래 열어 두지 않는다).
- 이미 main에 머지된 마이그레이션 파일은 수정하지 않는다. 새 마이그레이션을 추가한다.
- head가 2개가 됐을 때:
  ```bash
  uv run alembic heads                       # 2개 나오면
  uv run alembic merge heads -m "merge heads"
  ```

### 4-4. 브랜치 전략 (GitHub Flow)

```
main  ←── PR(리뷰 1명 승인) ←── feat/user-signup
                              ←── feat/post-crud
```

1. 작업 시작:
   ```bash
   git switch main
   git pull
   git switch -c feat/user-signup
   ```
2. 작업 중 자주 커밋하고, **하루 한 번은 main을 반영**한다:
   ```bash
   git fetch origin
   git rebase origin/main      # 또는 git merge origin/main
   ```
3. push 후 GitHub에서 PR 생성 → 상대방 리뷰 → **Squash and merge**
4. 머지 후 브랜치 삭제, 로컬 main pull

규칙:
- `main`에 직접 push하지 않는다.
- **PR은 작게** (가능하면 300줄 이하, 1~2일 안에 머지)
- PR이 크고 오래 열려 있을수록 충돌이 커진다.

### 4-5. GitHub 저장소 설정 (저장소 관리자가 1번)

Settings → Branches → Branch protection rule (`main`):
- ☑ Require a pull request before merging (Approvals: 1)
- ☑ Require status checks to pass (CI를 만든 뒤)
- Settings → General → Pull Requests에서 "Allow squash merging"만 켠다

### 4-6. 충돌이 났을 때

```bash
git fetch origin
git rebase origin/main
# 충돌 파일 수정 후
git add <파일>
git rebase --continue
git push --force-with-lease     # 내 브랜치에서만 사용. main에는 절대 쓰지 않는다
```
상대 코드가 섞인 충돌이면 혼자 판단하지 말고 같이 본다.

## 5. 커밋 / PR 컨벤션

```
feat: 회원가입 API 추가

chore: ruff 설정 추가
```

```markdown
## 작업 내용
-
## 관련 이슈
- close #
## 체크리스트
- [ ] 로컬에서 테스트 통과
- [ ] 마이그레이션 포함 여부 확인
- [ ] .env.example 변경 여부 확인
```

## 6. AI 도구를 함께 쓰는 법

- 둘 다 루트의 `CLAUDE.md`를 기준으로 AI를 쓴다. Cursor를 쓰면 `.cursorrules`나 `AGENTS.md`에 같은 내용을 링크하거나 복사한다.
- 규칙(폴더 구조, 응답 형식, 네이밍)이 바뀌면 **`CLAUDE.md`도 같은 PR에서 업데이트**한다. 그래야 AI가 둘에게 같은 스타일로 코드를 만들어 준다.
- AI가 만든 코드도 리뷰 대상이다. 특히 확인할 것:
  - 내 담당이 아닌 파일을 건드렸는지 (`git diff --stat`으로 확인)
  - 패키지를 마음대로 추가했는지
  - 마이그레이션 파일을 만들었는지
  - 비밀값을 하드코딩했는지
- AI에게 일을 시킬 때 범위를 명확히 준다. 예: "`app/domains/post/`만 수정해서 게시글 목록 API 추가해줘"

## 8. 프론트엔드와의 협업

- FastAPI가 자동으로 만드는 `/docs`(Swagger)와 `/openapi.json`을 API 명세로 사용한다.
- 엔드포인트를 만들 때 스키마를 먼저 정의하고 PR을 올리면 프론트가 바로 붙여 볼 수 있다.
- 에러 응답 형식은 초기에 한 번 정해서 공유한다. 예:
  ```json
  { "code": "USER_NOT_FOUND", "message": "사용자를 찾을 수 없습니다." }
  ```
